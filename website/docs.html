7aba-Lang documentation

Use the interpreter

Install the Windows interpreter, learn the core syntax, and find the current runtime behavior in one place.

7aba-Lang is experimental. The reference describes features currently implemented in the bytecode compiler; it is not a promise of a stable language standard.

Download and run

Download the Windows interpreter and save 7aba.exe beside your .7ba program. You do not need GCC or any C source files.

Download the interpreter
.\7aba.exe run .\your-file.7ba

Open PowerShell in that folder and run the command above, replacing your-file.7ba with your program's name. Keep the terminal open to see program output and errors.

The shorter command .\7aba.exe .\your-file.7ba is also supported. The included pro.7ba is a runnable example.

Your first program

Create a file named hello.7ba and run it with the interpreter:

action greet(name) {
    display "Hello, " name
}

greet("world")

action declares a callable function. display prints its values, and the final line calls the function.

Language reference

Statements are line-oriented. Expressions support integer and string literals, booleans, null, variables, collection indexing, calls, and arithmetic/comparison operators.

Variables and types

Variables are dynamically typed by default. Optional scalar annotations check the initial value and constrain later assignments:

count: Int = 3
ready: Bool = true
label: String = "ready"
empty_value: Null = null

count = count + 1

Supported annotations are Int, Float, Bool, String, and Null. Runtime tags must match exactly; implicit conversions are not applied.

Expressions

Arithmetic precedence is unary negation, multiplication/division, addition/subtraction, then comparisons. Parentheses group expressions. Integer overflow and division by zero report runtime errors.

total = 4 + 3 * 2
is_ready = total >= 10
message = "value: " + total

Array indexes start at zero. Map and set membership uses in. String comparisons and string search operations compare UTF-8 bytes, not Unicode grapheme clusters.

Control flow and actions

action report(score) {
    when score >= 80 {
        display "pass"
    }
    otherwise {
        display "try again"
    }
}

repeat 3 {
    display "once per iteration"
}

report(92)

Available control forms include when/otherwise, while, repeat, action calls, and empty to return from an action. try/catch and throw support integer exception payloads; not every runtime failure is catchable.

Classes and objects

class Counter {
    field value = 0

    action show() {
        display "count: " this.value
    }
}

counter = new Counter()
counter.value = 3
counter.show()

Classes support fields, constructors using init, methods, inheritance, and method overrides. Objects are managed runtime values but are not written by the scalar/collection persistence format.

Readable collection displays

Use display collection_name to get a structure-specific view:

  • Lists: bordered table with item indexes and values.
  • Piles: indexed values with the top-of-stack marker.
  • Matrices: row and column labels arranged as a grid.
  • Queues: FIFO order, front/back markers, and capacity status.

Empty lists, piles, and queues also have explicit empty-state output. These formatted displays apply to those collection commands; maps and sets use the regular value display.

list scores
push scores 12
push scores 24
display scores

queue jobs
enqueue jobs 31
enqueue jobs 42
display jobs

The list display includes rows like [0] 12. The queue display marks FRONT -> [0] and BACK -> [1], so the ordering is easy to inspect in the terminal.

Files and persistence

message = "hello from 7aba"
file_write "notes.txt" message overwrite
file_read "notes.txt" contents
file_display "notes.txt"

File read/display operations are bounded text operations. Relative paths are resolved from the process working directory. Global variables and supported collections may persist in a sidecar file named <script>.state; repeated runs can load and update this state.

String indexing, search, and case conversion are byte/ASCII based. They are not Unicode-aware text operations.

Runtime and implementation

A source program compiles to bytecode and executes in a stack VM. Each run owns a RuntimeContext with a managed heap, scopes, diagnostics, and execution budget.

Errors and known limits

  • Unsupported statements fail during compilation.
  • Some integer parsing, negation, and loop-count boundaries are not yet unified.
  • Unicode-aware columns and grapheme operations are not guaranteed.
  • Not all runtime errors can be caught with try/catch.
  • Module imports, package management, and concurrency are not implemented.
  • The whole-program AST and resolver are standalone tools, not the production statement pipeline.

The production compiler uses a line-oriented statement path and the expression AST. Program AST parsing and resolution are not integrated into production compilation.

Editor support and tests

The VS Code extension provides syntax highlighting, indentation, a run command, and basic language-service navigation.

For everyday use, download the interpreter above and use the extension's Run command. You do not need to build the C project.

Building the interpreter from C source and running the test suite are developer tasks. They require GCC and PowerShell:

cd vscode-extension
npm ci
npm test

To run the C unit and Windows integration tests from the repository root:

powershell -NoProfile -ExecutionPolicy Bypass -File .\tests\run_all.ps1

Developers building from source should use the strict flags -Wall -Wextra -Werror -O3 -std=c99. POSIX builds also link -lm -ldl.
